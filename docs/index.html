Every Cosmos DB application has a moment. It works in development. You deploy. And then three months later, someone opens a cost alert and asks — "Why is this burning 10x the RUs we expected?"

The cause is always the same — a wrong partition key, a query that fans out because nobody caught a missing filter, an index that was never added. The application runs fine. The logic is correct. But the Cosmos DB decisions underneath are wrong — and by the time you find out, changing them means a migration.

That is exactly what Agent Kit solves. We have packaged years of Cosmos DB best practices — from support cases, design reviews, and production incidents — into a skill you install with one command. Your coding agent gets deep Cosmos DB expertise built in.

One hundred and eleven rules across twelve categories — data modeling, partitioning, query optimization, SDK patterns, indexing, and more. It reviews your actual code and catches the mistakes before they ship to production.

So here is how it works end to end. Five steps, and the developer only does step one — the rest is automatic.

You run one install command. From that point forward, whenever your agent detects you are working on a Cosmos DB task, it loads SKILL.md as an index, picks the relevant rule files for your situation, and generates code that already follows best practices.

On the left you can see the install command and some example prompts. You just talk naturally — "help me choose a partition key", "optimize this query", "review my data model" — and the agent brings in the right rules.

On the right you can see every rule category we cover. Data modeling and partition key design are marked critical because those are the two decisions that cost the most to get wrong at scale. After that, query optimization, SDK best practices, vector search, and full-text search are all high impact.

The key insight: this is not generic NoSQL advice. These rules are specific to how Azure Cosmos DB works — its pricing model, its partition routing, its indexing engine, its SDK behavior. That specificity is what makes the difference between a helpful suggestion and a correct one.

And we test these rules. We have a testing framework that runs scenarios against the rules and measures pass/fail rates — so the rules actually get better release over release.
